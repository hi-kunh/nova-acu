> 만든 날: 2026-09-11 · 앞으로 대화가 많아질 것 같아 저장소 루트에 흩어져 있던 파일을 모두 옮겼습니다.

## 📢 DM 쪽에 알리는 것 (2026-09-11)

1. **문서 위치가 바뀌었습니다** — 저장소 루트 → **`dm/`**. 앞으로 질의·회신·자료는 **이 폴더에** 넣어 주십시오.
   파일 이름은 그대로라 문서 안의 서로 참조(`NCU_이벤트코드_질의_회신.md` 등)는 그대로 통합니다.
2. **파일 전달 중 두 파일이 뒤바뀌었습니다** (2026-09-11 오후 회신 때)
   - `NCU_장치구조_프로토콜_안내.md` 자리에 **질의서 내용**이 들어갔고, 질의서 파일은 지워졌습니다
   - 정리해 보내 주신 장치구조 문서는 **파일 이름이 CP949로 깨진 새 파일**로 들어왔습니다
   - NCU 쪽에서 내용을 비교해 **제자리로 돌렸습니다**: 질의서 = git 원본, 장치구조 = 보내 주신 정리본 (내용 변경 없음)
   - ⇒ 한글 파일 이름을 **UTF-8로 저장**해 주시고, 받은 문서를 고칠 때는 **다른 파일에 덮어쓰지 않았는지** 한 번 확인 부탁드립니다
3. 질의 1~7 회신은 잘 받아 반영했습니다. **추가로 실측을 요청드릴 목록**은 아래 "진행 중"에 있습니다.

## 파일 규칙

| 규칙 | 내용 |
|------|------|
| 위치 | 모든 질의·회신·자료는 `dm/` |
| 질의 | `NCU_<주제>_질의.md` (NCU → DM) — Platinum 앞 질의는 `Platinum_<주제>_질의.md` |
| 회신 | **질의 파일 이름 + `_회신`** (예: `NCU_DM_질의_RRU구성_이벤트보관_회신.md`) — 새 파일로 만들고 질의 파일은 고치지 않는다 |
| 규약·안내 | `NCU_<주제>_안내.md` — 고칠 때는 문서 안에 날짜와 정정 내용을 남긴다 |
| 자료 | 표·덤프는 설명이 되는 이름으로 (`event_codes_all.csv`) |
| 인코딩 | 파일 이름·내용 모두 **UTF-8** |
| 목록 | 새 파일을 넣으면 아래 "문서 목록"에 한 줄 추가 |

## ✅ 2026-09-14 저녁 — DM 회신으로 막혀 있던 것이 거의 다 풀렸다

`DM_회신_Object번호확정_원시바이트_20260914.md`. 우리가 요청한 것을 **전부** 주었다.

### 받은 것

| | 내용 |
|---|------|
| 🔴 | **정정 수용** — `SettingInputValueChange`는 동작하지 않는다. DM이 확정 목록에서 뺐고, *"쓰기는 동작합니다"* 도 **철회**했다.<br>근거: `ncu01`의 설정 성공 이벤트(`10210301`/`10220301`)가 **등록 이래 0건**, 같은 날 ACU04는 16건 |
| 🟢 | **Object 7개 확정** (DM 소스 `DeviceObject` 열거형 — 추정이 아니라 정의값) |
| 🟢 | **원시 바이트 3종** — 요청·응답 양쪽 전부. 컨트롤러 기본(13byte) · 입력(21byte) · **출력(14byte, 신규)** |
| 🟢 | **헤더 44byte 전체 지도** — 우리가 못 찾던 "어느 칸을 묻는가"의 답 |
| 🟢 | **카드 이벤트 실측** — `ModuleAddress=02`, `ReaderAddress=01`. **1부터, 원시 바이트 그대로**. 우리 수정이 맞았다 |
| 🟡 | 덤 — 현장 SSC-324가 **이벤트 읽기 인덱스** 때문에 이벤트를 하나도 못 올린 고장. NCU가 피해야 할 함정 |

### 🔴 우리 추정이 틀린 것 하나

```
0x2f (47)  = CardReader        <- 이것이 카드리더다
0xa6 (166) = DeviceGroupApply  <- 우리는 카드리더로 추정했다. 틀렸다
```

**"반복 횟수 = 포인트 수" 규칙은 포인트 단위 설정(입력·출력·리더)에만 적용된다.**
그룹·스케줄·알람은 다른 축으로 반복한다 — `0xa6`가 4회 온 것은 우연의 일치였다.

### 🔴 가장 큰 것 — 칸 선택은 `AddressDestBroadcast` 비트맵이다

```
헤더 offset 11~14  AddressDestBroadcast = 32비트 비트맵. 켜진 비트 = 대상 포인트

Obj 0x29 (컨트롤러)  Broadcast 00 00 00 00    비트맵 없음
Obj 0x2c (입력)      Broadcast 00 00 00 04    bit2
Obj 0x2d (출력)      Broadcast 00 00 01 00    bit8

StartDataBlockIdx/End/Count 는 세 요청 모두 00 01 — "몇 개짜리 묶음인가"만 말한다
```

⚠ **`StartDataBlockIdx`만 보고 만들면 "언제나 1번 칸만 돌려주는 장비"가 된다.**
🟡 비트 번호 ↔ 포인트 번호 대응은 DM이 입력 1~16을 훑어 **표로 만들어 주기로** 했다.

### 🟢 출력 설정 14byte — 알람 릴레이 규칙의 근거

| off | len | 필드 | 비고 |
|---:|---:|---|---|
| 0 | 4 | AccessOption | bit31 = 사용함 |
| 4 | 1 | ReactionModuleAddress | **입력 쪽에서** 어느 출력을 깨울지 가리킬 때 쓴다 |
| 5 | 1 | ReactionDeviceAddress | 〃 |
| 6 | 1 | **ActiveType** | **2 = Alarm** ← 알람 릴레이 규칙의 핵심 |
| 7 | 1 | ActiveTime | 동작 시간(초) |
| 8 | 1 | DelayTime | |
| 9 | 1 | ActiveTimeHandicap | |
| 10 | 1 | **IsActiveOption** | **bit7 = 화재로 동작, bit6 = 협박으로 동작** |
| 11 | 3 | Reserved | |

⇒ **`ActiveType=2`인 출력은 보드 전체에서 전부 동작하고, 화재로도 울릴지는 `IsActiveOption` bit7이 정한다.**

### 🔴 우리가 답해야 할 것 — 답했다

DM이 물었다: *"버린 요청에 성공 ACK가 나간 것 아닌가"*

**실측했다. acud는 지원하지 않는 요청에 응답을 전혀 보내지 않는다.**
같은 프레임(`Cmd 5 / Sub 5 / Obj 0x2c`)을 보내고 3초 기다려 **타임아웃**을 확인했다.
⇒ DM 로그의 `AckResult = 1`은 **DM 쪽 기본값**이다.
