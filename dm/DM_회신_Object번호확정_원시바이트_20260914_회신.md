## 1. 🟢 성공 ACK — 실측했습니다. 저희가 보낸 것이 아닙니다

DM 쪽에서 *"버린 요청에 성공 ACK가 나간 것 아닌가"* 물어 주셔서 바로 재봤습니다.

**DM이 09:54:36에 보낸 것과 같은 프레임**을 acud에 보내고 3초를 기다렸습니다.

```
보냄   Cmd 5 / Sub 5 / Obj 0x2c (입력 설정 쓰기), 데이터 21byte
받음   응답 없음 (타임아웃)
```

소스에서도 같습니다 — 지원하지 않는 요청은 **로그만 남기고 아무것도 보내지 않습니다.**

```c
/* net.c handle_request() 끝 */
snprintf(line, ..., "네트워크: 지원하지 않는 요청 (cmd=0x%02x sub=0x%02x obj=0x%02x) 무시", ...);
log_msg(line);          /* <- 여기서 끝. send_response() 를 부르지 않는다 */
```

⇒ **DM 로그의 `AckResult = 1`은 DM 쪽 기본값으로 보입니다.** 소스 확인에 참고가 되면 좋겠습니다.

### 🟡 그런데 "무응답"이 맞는 답일까요 — 저희가 묻습니다

DM 쪽에서 *"미구현 명령에는 실패 ACK 또는 무응답이 맞다"* 고 하셨는데, 둘 중 **어느 쪽이 나은지**
정해 주시면 그대로 하겠습니다.

| | 장점 | 단점 |
|---|------|------|
| **무응답**(지금) | 장비가 모르는 것에 답을 지어내지 않는다 | **DM이 타임아웃을 기다린다** — 폴링이 그만큼 느려진다 |
| **실패 ACK** | DM이 곧바로 다음으로 넘어간다 | 프레임 형식이 명령마다 달라, 무엇으로 답할지 정해야 한다 |

🟡 저희 생각으로는 **실패 ACK가 낫습니다** — 현장에서 미구현 명령이 남아 있는 동안
DM 폴링이 느려지는 것이 더 나쁘기 때문입니다. **DM이 그 실패를 "장비 고장"으로 읽지 않는다면** 그렇습니다.
그쪽 화면에서 어떻게 보이는지 알려 주십시오.

## 2. 🔴 `0xa6` — 저희가 틀렸습니다

```
0x2f (47)  = CardReader        <- 이것이 카드리더
0xa6 (166) = DeviceGroupApply  <- 저희는 카드리더로 추정했습니다
```

**짚어 주신 이유가 정확합니다.** 저희는 *"반복 횟수 = 포인트 수"* 규칙을 `0xa6`의 4회에 적용했는데,
그 규칙은 **포인트 단위 설정(입력·출력·리더)에만** 쓰이는 것이었습니다.
그룹·스케줄·알람은 다른 축으로 반복하니 4회는 우연의 일치였습니다.

⇒ 저희 문서(`dm/README.md`)를 고쳤습니다. **`0x2f`를 카드리더로 넣고 `0xa6`는 뒤로 미룹니다**
(엑세스그룹은 SSC-324에서도 실패 중이라고 하셨으니 우선순위 가장 뒤로 두겠습니다).

> 🟡 **숫자가 맞아떨어졌다고 맞는 것이 아니라는 걸 다시 배웠습니다.** 앞으로 로그에서 역산한 값은
> "추정"이라고 분명히 적고, 정의값을 받기 전까지 구현에 쓰지 않겠습니다.

## 4. 🟡 6절 이벤트 인덱스 — 저희 설계에도 같은 구멍이 있었습니다

보내 주신 고장 사례(읽기 인덱스가 쓰기보다 앞서 나가 "새 이벤트 없음"으로 답하는 것)를 받고
저희 `events.db`를 다시 봤습니다. **같은 모양의 구멍이 있습니다.**

```c
/* events.c events_pending() */
pending = max_seq - sent;          /* sent 가 max 보다 크면 음수 -> 0 을 돌려준다 */
return (pending > 0) ? pending : 0;
```

정상 동작에서는 `sent`가 `max`를 넘을 수 없지만, **DB를 갈아 끼우거나 복구했을 때** 넘을 수 있고
그러면 **영영 0건**이 됩니다. 정확히 말씀해 주신 그 고장입니다.

**9/17에 이렇게 고치겠습니다.**

| | 내용 |
|---|------|
| ① | **읽기 위치가 쓰기 위치보다 앞서면 자동으로 되돌린다** (`sent > max` 이면 `sent = max`) — 로그를 남긴다 |
| ② | `EventCountCheck` · `EventIndexChange` · `EventReset` **세 명령 구현** |
| ③ | 링 되감김(오래된 것 삭제) 경계를 시험한다 — 저희는 1,000만 건에서 1,000건씩 지웁니다 |
| ④ | 가능하면 **읽기/쓰기 위치를 함께 돌려주겠습니다** — 말씀하신 대로 그게 훨씬 낫습니다 |

🙏 **`EventIndexChange`의 타입 3(지정 시각부터) · 타입 4(시작~끝 구간) 원시 바이트**를
주실 수 있으면 그대로 맞추겠습니다. 없으면 저희가 규약 안에서 정하고 초안을 보내 드리겠습니다.

> **이 제보가 가장 값졌습니다.** 없었으면 저희도 같은 자리에 같은 고장을 만들어 놓고
> 현장에서 찾고 있었을 겁니다. 감사합니다.
