## 1. 모듈 번호를 띄워도 됩니다

서버와 Platinum 모두 `devmoduleenabled` 를 **한 칸씩 독립적으로** 봅니다. 연속성을 요구하는 코드가 없습니다.

```
DM        SyncDeviceIONameV2 / SaveDownloadedStructure
          for (i = 0..13)  if (enabled[i] == '1') { … }
Platinum  UpdateTotalDeviceInfoDataReocrd
          if (devmoduleenabled.Substring(i,1) == "1") { … }
```

- **1-1** `IsExistModule [B0][B1] = 00 33` → `devmoduleenabled = 11001100000000` 으로 들어가고
  **모듈 1·2·5·6 의 포인트가 생성**됩니다.
- **1-2** 이벤트는 `(모듈, 슬롯)` 좌표를 그대로 저장하고, Platinum 은 `deviceioname_tbl` 에서
  같은 좌표로 이름을 찾습니다. 모듈 5·6 의 이름 행도 같이 만들어지므로 **정상 표시됩니다.**
- **1-3** ⇒ **건너뛰기 금지 규칙은 두실 필요 없습니다.**

🟡 다만 두 가지:

```
· IsExistModule 은 16비트지만 서버는 **앞 14개만** 씁니다. 모듈 15·16 자리는 버려집니다
· 실측은 못 했습니다 — 현장 SSC-324 에 확장보드가 없어 모듈 3 이상을 만들 수 없습니다
  ⇒ 위는 **코드를 읽고 드리는 답**입니다. NCU 로 모듈 1·2·5·6 을 보고해 보시면 바로 실증됩니다
```

## 2. 운영 중 `IsExistModule` 을 바꾸는 것 — 🔴 **(B)를 권합니다**

### 🔴 핵심 — **폴링은 `IsExistModule` 을 읽지 않습니다**

폴링 응답에서 서버가 DB 에 반영하는 것은 **세 가지뿐**입니다.

```
devdatetime                  장비 시각
devmodule<N>iostatus         IO 상태 니블
devcontrollercommstatus      통신 상태
```

**구조(`devmoduleenabled`·`iocategory`)는 "장치구조 다운로드" 에서만 갱신됩니다.**

- **2-1** ⇒ (A)로 bit 를 내려도 **서버는 알아채지 못합니다.** 포인트도 그대로 남습니다.
  반영시키려면 장치구조 다운로드를 다시 해야 하는데, 그때는
  `deviceioname_tbl` 이 그 컨트롤러 것을 **통째로 지우고 다시 만듭니다.**
  🔴 그리고 **Platinum 이 만든 리더/입출력 행은 사라진 모듈 것이 남을 수 있습니다** —
  실제로 오늘 `ncu01` 에서 6모듈 → 4모듈로 줄였을 때 겪었습니다.
  ⇒ **운영 중 구조를 흔들면 포인트가 어긋납니다.**

- **2-2** 끊긴 모듈을 나타낼 **규약 값이 없습니다.** 상태는 `iostatus` 의 하위 니블인데
  "부재/끊김"에 해당하는 정의된 값이 표에 없습니다. 임의 값을 쓰면 화면에 숫자로만 뜹니다.

- **2-3** 모듈 존재/부재를 보여주는 **전용 화면이 없습니다.** Platinum 의 모듈 입출력 화면은
  `iocategory`/`iostatus` 를 읽어 포인트를 그릴 뿐이고, 장치 트리는 **포인트 행 기준**이라
  구조를 다시 받기 전에는 바뀌지 않습니다.

⇒ **정리: `IsExistModule` 은 설치 구성대로 고정하고, USB 단절은 이벤트(`0x20030102`)로만 알리십시오.**
서버가 "지금 몇 번 모듈이 살아 있나"를 표시할 방법이 애초에 없습니다.

## 3. 이벤트 주소 원시 바이트 — **1부터 셉니다**

파서가 가공을 하지 않습니다.

```
isldev\clsDevEvent.cs
  ModuleAddress = Convert.ToInt32(bEvent[offset 6])
  ReaderAddress = Convert.ToInt32(bEvent[offset 7])
```

**DB 에 보이는 값이 곧 원시 바이트입니다.**

- **3-1** 모듈1 슬롯13 알람 → DB `(1, 13)` ⇒ 원시 **`0x01 0x0D`**

- **3-2** SSC-324 카드 이벤트는 **아직 실측이 없습니다** — 현장에서 그 리더에 태그가 일어나지 않습니다.
  다만 같은 체계라는 증거는 오늘 충분히 나왔습니다:

```
10210301 (입력 설정 변경)  →  (1,14) · (2,14)          ← 입력 슬롯 그대로
10220301 (출력 설정 변경)  →  (1,9) · (1,10) · (2,11)  ← 출력 슬롯 그대로
18010306 (알람)            →  (1,13) · (2,13)
ACAM 카드 이벤트           →  (1,1) · (1,2)            ← 리더 슬롯 그대로
```

  ⇒ 리더도 **`0x01 0x01` · `0x01 0x02`** 로 봅니다. 현장에서 카드 한 번 태그하면 확정됩니다.

- **3-3 USB 단절** — 서버에는 규칙이 없습니다(코드와 주소를 그대로 저장·표시할 뿐).
  **권고: RRU 단위로 1건.**

```
Module Address = 그 RRU 의 첫 모듈 번호
Reader Address = 0
```

  근거: 리더가 아닌 사건은 `(0,0)` 으로 오는 선례가 이미 있고(화재·정전·전원투입),
  모듈마다 1건씩 올리면 **같은 사건이 화면에 두 줄**로 보입니다.

## 4. 이벤트 보관과 일괄 업로드

### 4-1 한 프레임에 실을 수 있는 양 — **약 1,810건**

```
프레임 길이 필드가 2바이트  →  한 프레임 최대 65,535 바이트
  헤더(V2)           44
  장치상태          234      ← FrameOptIsExcludeDeviceStatus 로 뺄 수도 있습니다
  CS + ETX          2~4
  ─────────────────────
  데이터 가용      약 65,253 바이트  →  36바이트 이벤트 기준 **약 1,810건**
수신 버퍼도 65,584 바이트입니다
```

🔴 **건수는 헤더가 알려 줘야 합니다.** DM 은 `데이터 길이 ÷ OneDataBlockSize` 로 셉니다.

```
헤더 오프셋 42  OneDataBlockSize(2바이트)   ← 이벤트 한 건의 크기(36)를 넣으십시오
헤더 오프셋 36  StartDataBlockIdx(2)
헤더 오프셋 38  EndDataBlockIdx(2)
헤더 오프셋 40  CountDataBlockIdx(2)
분할이 필요하면 CurrFrameIdx(오프셋 20) · EndFrameIdx(오프셋 22)
```

### 4-2 ~ 4-5 — 🔴 **서버 코드로는 답할 수 없습니다**

EventCountCheck 의 건수가 "전체"인지 "미전송"인지, EventIndexChange 뒤 장비가 어떻게 움직이는지,
EventReset 이 삭제인지 포인터 초기화인지는 **전부 장비 동작**입니다.
DM 은 명령을 보내고 응답을 해석할 뿐 의미를 규정하지 않습니다.

🟢 **다만 실측할 수 있습니다.** 세 명령 모두 DM 에 등록돼 있어 Platinum 에서 누를 수 있습니다
(`CommandProcessor.cs:67~69`). **요청 주시면 현장 SSC-324 로 재서 회신하겠습니다.**

### 4-6 수십만 건이 한꺼번에 올라올 때

DM 은 이벤트 **1건마다** 이렇게 합니다:

```
eventlog_tbl INSERT  →  정책 검사(이벤트코드 조회)  →  (이미지가 있으면) 별도 INSERT
```

폴링 스레드가 DB 락을 잡고 **순차로** 처리합니다. 수십만 건이 한 번에 오면
**그동안 다른 장비의 폴링이 밀립니다.**

🟡 **권고(실측값 아님): 한 응답에 200~500건으로 끊고, 나머지는 다음 폴링에서 이어 올리십시오.**
폴링 주기가 3초이므로 500건씩이면 분당 1만 건입니다. 정확한 한계는 재 봐야 알 수 있고,
필요하시면 그 시험도 같이 하겠습니다.

### 5-2 한 칸씩 보냅니다

오늘 실측 — Platinum 이 입력 네 칸을 바꾸자 **명령이 네 번** 나갔습니다.

```
[2:1:13]  [2:1:14]  [2:2:13]  [2:2:14]     ← 컨트롤러:모듈:슬롯
```

프레임 규격상 블록을 여러 개 담을 수 있지만(`StartDataBlockIdx`/`EndDataBlockIdx`),
**현장 동작은 한 칸씩**입니다. 대체 목적이라면 **한 칸씩 받는 것만 구현해도 충분**합니다.

### 5-3 **1부터 셉니다**

실측입니다 — 반응 장치에 `2` 를 주니 이벤트가 `(2,2)`(리더2)로 왔고,
`11` 을 주니 **출력 슬롯 11** 이 동작했습니다. 모듈·슬롯과 **같은 좌표 체계**입니다.

## 6. 대기 항목

### 6-1 🟢 화재 주소 재측정 완료

```
반응 (1,2)  리더2  →  이벤트 (1,2)
반응 (2,2)  리더2  →  이벤트 (2,2)
반응 (1,11) 출력   →  이벤트 (0,0)
반응 (2,11) 출력   →  이벤트 (0,0)
```

⇒ **규칙: 반응 장치가 "리더" 면 그 리더 주소, 리더가 아니면 `(0,0)`.**
이벤트의 module/reader 자리는 원래 "어느 **리더**에서 일어났나"를 담는 곳입니다.

🟡 **반응이 아예 설정되지 않은(0) 화재 입력은 아직 안 재 봤습니다.** 리더가 아니므로 `(0,0)` 으로 봅니다.

### 6-1-보충 🟢 릴레이 연동 규칙 — **오늘 실측으로 확정했습니다**

```
알람 · 화재 모두  →  **동작 종류가 Alarm 인 출력만** 동작합니다
                     여러 개면 **전부**, 그리고 **보드 전체**(모듈1 입력이 모듈2 출력까지)에서

실측:  모듈1 Alarm = 슬롯10        → 슬롯10 만 동작
       모듈2 Alarm = 슬롯9·슬롯11  → 둘 다 동작
       (Alarm 종류를 슬롯9 → 슬롯10 으로 옮기자 동작하는 출력도 따라 옮겨갔습니다)

반응 장치 설정은 **릴레이 대상과 무관**합니다 — 반응을 6·5·1·10·11·2 로 바꿔도 동일했습니다.
반응 설정은 **화재 이벤트의 주소에만** 영향을 줍니다(6-1 참조).
알람 릴레이는 출력 설정의 동작시간(3초)보다 **오래 유지**됐습니다(약 12초) — 알람 상태를 따라가는 듯합니다.
```

🔴 **이 규칙에 도달하기까지 네 번 틀렸습니다.** 원인은 하나였습니다 —
**DB 의 설정값이 장비에 안 들어가 있었습니다.** 자세한 것은 6-1-보충2.

### 6-1-보충2 🔴 **DB 설정값 ≠ 장비 설정값** — NCU 쪽에도 중요합니다

한 출력이 "DB 상 Door 인데 알람에 반응" 해서 없는 규칙을 만들어 냈는데,
그 칸의 설정이 **장비에 한 번도 전송된 적이 없었습니다**(`outputrelay_updated` 가 이틀 전).
한 번 전송하자 바로 규칙대로 동작했습니다.

⇒ **설정이 장비까지 갔는지는 이벤트로 확인하십시오.**

```
10210301   Data > Input  > Change > Success    입력 설정이 장비에 들어갈 때마다 1건
10220301   Data > Output > Change > Success    출력 설정이 장비에 들어갈 때마다 1건
```

🟢 **NCU 도 이 두 이벤트를 올려 주십시오.** 설정 전송의 성공을 서버가 확인하는 유일한 표식이고,
되읽기 없이 쓸 수 있어 운영 중 진단에 그대로 쓰입니다.

### 6-1-보충3 🟢 화재 정책이 실제로 도는 것을 확인했습니다

```
18010401 화재 발생  →  (3~7초)  →  18010119  Door Forced Open Mode
18010402 화재 복구  →  (4~6초)  →  1801011a  Door Normal Mode      ← 자동 원복
```

**네 번 연속 재현**됐습니다. NCU 가 `18010401`/`18010402` 를 올리기만 하면
DM 이 대상 컨트롤러에 강제개방·해제를 넣습니다. **NCU 쪽에서 문을 직접 열 필요가 없습니다.**

🟡 정책이 도는 동안 **DM 의 폴링이 잠시 멈춥니다**(1초 + 대상 수 × 300ms).
화재 시 이벤트가 몇 초 늦게 올라올 수 있으니, NCU 는 그동안의 이벤트를 **버리지 말고 보관**해야 합니다.

### 6-2 🔴 아직 확인 못 했습니다

서버의 `ncu01` 장치구조는 **여전히 `11110000000000`(모듈 4개)** 이고 포인트도 리더 8·입력 32·출력 16 입니다.
**장치구조 다운로드를 다시 하셔야 반영됩니다**(2절 참고 — 폴링으로는 안 바뀝니다).
하시면 바로 확인해서 알려드리겠습니다.

### 6-3 🟢 SSC-324 의 `mType` 은 **61**

```
SSC-324 (ACU03·ACU04)   devmodule1·2 modeltype = 61   installedtype = 1
ncu01 (현재)            modeltype = 123               installedtype = 2
```

⇒ **대체 목적이라면 `mType = 61`, `installedtype = 1` 로 맞추시는 것을 권합니다.**
서버는 이 값을 화면 표시에만 쓰고 판정에는 안 쓰지만, 같은 장비로 보이려면 같아야 합니다.

### 6-4 MultiLanguage — 실측 필요

현장 SSC-324 에 해당 명령을 눌러 본 기록이 없습니다. 요청 주시면 재겠습니다.

## 7. 사용자 한도

### 7-1 DM 이 들고 있는 상한은 **100,000명**

```
isldev\clsDevParams.cs
  UserBinDataObjectCountMax_SSC   = 100000      ← 카드 모델
  UserBinDataObjectCountMax_SSCFP =  20000      ← 지문 모델
```

🔴 이것은 **장비의 실제 한도가 아니라 DM 이 검사에 쓰는 값**입니다.
매뉴얼의 `130,000 / 260,000` 과 다릅니다 — 실제 장비가 몇 명까지 받는지는 서버가 모릅니다.

### 7-2 **DM 이 막습니다**

```
isldev\clsDevUserBin.cs:1084
  if (devUserInfos.Length <= UserBinDataObjectCountMax_SSC) { isProcContinue = true; }
```

상한을 넘으면 **전송을 시작조차 하지 않습니다.** 장비까지 가지 않으므로 장비 응답도 없습니다.
⇒ NCU 가 10만 명 넘게 받을 수 있어도 **DM 이 먼저 자릅니다.**

### 7-3 지문·사진 — 현장 확인 사항

서버에는 두 경로가 다 있습니다(`usertemplate_tbl`·`userpictbl`, `UserBinTrans` 에 이미지 옵션).
현장에서 실제로 쓰는지는 저희가 단정할 수 없어 사용자께 확인 요청드렸습니다.

### 7-4 **둘 다 있습니다**

```
바이너리 일괄  UserBinTransSendStart / UserBinTransSendContinue   (총 크기·총 인원·프레임 인덱스)
1명씩          UserSend / UserReceive / UserDelete / UserRegisterCheck
```

전체 다운로드는 바이너리 일괄을 쓰고, 개별 변경은 1명씩 명령을 씁니다. **양쪽 다 구현이 필요합니다.**
