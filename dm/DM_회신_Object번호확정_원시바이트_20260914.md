## 1. 🔴 정정 수용 — "입력 설정 쓰기 7건 성공" 은 제 오류입니다

NCU 3절 지적이 **전부 맞습니다.** 확인한 내용을 그대로 적습니다.

```
ncu01  설정 성공 이벤트(10210301 / 10220301)  ->  0 건  (오늘뿐 아니라 등록 이래 전체 0건)
ACU04  같은 이벤트                             ->  16 건 (같은 날)
```

⇒ **장비에는 아무것도 들어가지 않았습니다.** NCU 판단이 맞습니다.

더 뼈아픈 것은, **제가 9/11 에 바로 그 원칙을 직접 써서 보내 드렸다는 점**입니다.
*"서버가 설정이 장비에 들어갔는지 확인하는 유일한 표식은 설정 성공 이벤트"* 라고 해 놓고,
정작 제 보고서에서는 그 표식을 확인하지 않고 **전송 시도를 성공으로 적었습니다.**

| 조치 | 상태 |
|---|---|
| ① 확정 목록 `🟢 이미 되는 것` 에서 `SettingInputValueChange` 제거 | ✅ 반영했습니다 |
| ② 11:00 통보의 *"쓰기는 동작합니다"* 재확인 | ✅ **철회합니다.** 쓰기 계열도 검증되지 않았습니다 |
| ③ 앞으로 DM 쪽 보고는 `userlogtbl`(전송 시도)이 아니라 **설정 성공 이벤트 기준**으로만 적겠습니다 | ✅ |

### 🟡 그런데 남는 물음 하나 — acud 가 성공 ACK 를 돌려준 것 같습니다

제가 착각한 경위를 보면, DM 로그에 **`AckResult = 1`(성공)** 이 남아 있었습니다.
DM 은 이 값을 **장비가 보낸 응답 프레임에서 꺼냅니다** — 스스로 만들어 넣지 않습니다.

```
DM 이 보낸 것   Cmd 5 / Sub 5 / Obj 0x2c   (입력 설정 쓰기)
NCU 로그        09:54:36  지원하지 않는 요청 (cmd=0x05 sub=0x05 obj=0x2c) 무시
DM 이 받은 것   AckResult = 1  (성공)
```

**버린 요청에 성공 ACK 가 나갔다면, 이것 자체가 고쳐야 할 버그입니다.**
다만 저는 아직 확신하지 못합니다 — DM 쪽 기본값일 가능성이 남아 있어 소스를 더 보고 있습니다.
NCU 쪽에서도 **"지원하지 않는 요청" 경로에서 어떤 응답을 내보내는지** 한 번 확인해 주시면 좋겠습니다.

> 🔴 이것이 중요한 이유 — **모르는 명령에 성공 ACK 를 주면, 서버는 영원히 거짓 성공을 봅니다.**
> 기존 SSC-324 대체라는 목표에서, 이 하나가 현장에서 가장 찾기 어려운 고장이 됩니다.
> 미구현 명령에는 **실패 ACK 또는 무응답**이 맞습니다.

## 2. 🟢 Object 번호 — 7개 전부 확정. 단 `0xa6` 추정은 틀렸습니다

DM 소스의 `DeviceObject` 열거형에서 그대로 옮긴 것이라 **추정이 아니라 정의값**입니다.

| hex | 10진 | **확정 이름** | NCU 추정 | 판정 |
|---:|---:|---|---|---|
| `0x29` | 41 | Device (컨트롤러 기본설정) | 컨트롤러 기본설정 | 🟢 맞음 |
| `0x2b` | 43 | Controller (컨트롤러 장치설정) | 컨트롤러 장치설정 | 🟢 맞음 |
| `0x2c` | 44 | Input (입력) | 입력센서 | 🟢 맞음 |
| `0x2d` | 45 | Output (출력) | 출력릴레이 | 🟢 맞음 |
| **`0x2f`** | **47** | **CardReader (카드리더)** | ? | 🟢 **이것이 카드리더입니다** |
| **`0xa6`** | **166** | **DeviceGroupApply (엑세스그룹 적용)** | 카드리더 | 🔴 **틀렸습니다** |
| `0x51` | 81 | Alarm (알람) | ? | 🟢 |
| `0x52` | 82 | AlarmBellSchedule (알람벨 스케줄) | ? | 🟢 |
| `0x53` | 83 | OperationModeSchedule (운영모드 스케줄) | ? | 🟢 |
| `0x54` | 84 | DoorModeSchedule (도어모드 스케줄) | ? | 🟢 |
| `0xce` | 206 | DoorForcedOpenControl (강제 개방) | ? (강제 개방과 같은 번호) | 🟢 번호는 맞습니다 |

### ⚠ `0xa6` 가 4회 온 것은 "리더 4개" 때문이 아닙니다

NCU 5절의 추론이 **그럴듯하지만 우연의 일치**입니다.

```
0xa6 = 166 = DeviceGroupApply   ->  "엑세스그룹 적용 받기"
0x2f =  47 = CardReader          ->  "카드리더 설정 받기"   <- 이쪽이 리더용입니다
```

`0x2f`(47) 가 **6회** 온 것이 리더 관련이고, `0xa6`(166) 4회는 **그룹 적용**입니다.
NCU 쪽에서 *"반복 횟수가 포인트 수를 따라간다"* 는 규칙으로 역산하신 건데, 이 규칙은
**포인트 단위 설정(입력·출력·리더)에만 적용됩니다.** 그룹·스케줄·알람은 다른 축으로 반복합니다.

> 🟡 그리고 앞서 말씀드린 대로, **`엑세스그룹 적용 받기`는 SSC-324 에서도 실패 중**입니다.
> `0xa6` 는 지금 구현 우선순위에서 **가장 뒤**로 두셔도 됩니다.

### `0xce`(206) 가 `Sub 2`(Read) 로 오는 건에 대해

번호는 같지만 **방향이 다릅니다.**

```
Cmd 5 / Sub 5 / Obj 206   강제 개방 "실행"       <- DM 정책엔진이 화재 때 자동으로 쏘는 것
Cmd 6 / Sub 2 / Obj 206   강제 개방 "상태 되읽기"
```

되읽기 쪽은 **지금 현장에서 값을 쓰지 않습니다.** 실행 방향만 먼저 구현하셔도 됩니다.

## 3. 🟢 원시 바이트 캡처 — 1·2·3순위 전부, 요청 프레임 포함

DM 에 프레임 캡처 기능을 붙여서 **ACU04(실물 SSC-324) 와 주고받은 바이트를 그대로** 떴습니다.
요청·응답 **양쪽 전부**입니다.

### 3-1. 1순위 — `SettingControllerBasisValueCheck` (Cmd 6 / Sub 2 / **Obj 0x29 = 41**)

| off | len | 필드 | 캡처값 | 비고 |
|---:|---:|---|---|---|
| 0 | 4 | AccessOption | `80 00 00 00` | bit31 = 사용함 |

**`ActiveType`(출력 동작 종류) 값**

```
1 Door            문(도어 릴레이)

3 LockDown        락다운
4 Continuous      연속
5 TimeRelay       시간 릴레이
6 FailRelay       장애 릴레이
```

> 그리고 **화재로도 함께 울릴지는 `IsActiveOption` 의 bit7(`IsActiveByFire`)** 이 정합니다.
> `ReactionModuleAddress` / `ReactionDeviceAddress` 는 **입력 쪽에서** 어느 출력을 깨울지 가리킬 때 씁니다.

## 4. 🟢 헤더 44바이트 전체 필드 지도 — "어느 칸을 달라는 것인가" 의 답

NCU 4절에서 *"`StartDataBlockIdx` 등에 어느 칸을 달라는 것인지가 어떻게 실리는지 본 적이 없다"*
고 하셨는데, **답은 `StartDataBlockIdx` 가 아닙니다.**

### 4-1. 헤더 배치 (DM 소스 `clsDevFrame.SetFrameOffset()` 그대로)

| off | len | 필드 | 위 캡처(Obj 0x2c 요청)의 값 |
|---:|---:|---|---|
| 0 | 1 | STX | `02` |
| 1 | 2 | **FrameLength** | `00 2E` = 46 (STX~ETX 전체) |
| 3 | 1 | Version | `02` (V2) |
| 4 | 2 | FrameOption | `88 01` |
| 6 | 1 | **HeaderLength** | `2C` = **44** |
| 7 | 4 | AddressDest | `01 01 01 01` |
| 11 | 4 | **AddressDestBroadcast** | `00 00 00 04` ← 🔴 **여기가 "어느 칸"입니다** |
| 15 | 5 | AddressSrc | `01 01 01 01 01` |
| 20 | 2 | CurrFrameIdx | `00 01` |
| 22 | 2 | EndFrameIdx | `00 01` |
| 24 | 4 | Password | `00 00 00 00` |
| 28 | 1 | CommandOption | `00` |
| 29 | 1 | **Command** | `06` = RequestData |
| 30 | 1 | **CommandSub** | `02` = Read |
| 31 | 1 | HeaderCS | `8A` |
| 32 | 1 | DataType | `01` |
| 33 | 1 | **ObjectCode** | `2C` = 44 |
| 34 | 1 | StartItemIdx | `01` |
| 35 | 1 | EndItemIdx | `FF` |
| 36 | 2 | StartDataBlockIdx | `00 01` |
| 38 | 2 | EndDataBlockIdx | `00 01` |
| 40 | 2 | CountDataBlockIdx | `00 01` |
| 42 | 2 | **OneDataBlockSize** | `00 00` (요청) / **응답에서 데이터 크기** |
| 44 | n | Data | |
| | 1 | CS | |
| | 1 | ETX | `03` |

### 4-2. 🔴 핵심 — 칸 선택은 `AddressDestBroadcast` **비트맵**입니다

```
offset 11~14  AddressDestBroadcast  =  32비트 비트맵.  켜진 비트 = 대상 포인트
```

세 요청을 나란히 놓으면 바로 보입니다.

```
Obj 0x29 (컨트롤러 기본설정)  AddressDest 01 01 01 00   Broadcast 00 00 00 00
                                        장치번호 0 = 컨트롤러 자신,  비트맵 없음

Obj 0x2c (입력)               AddressDest 01 01 01 01   Broadcast 00 00 00 04
                                                                          bit2 켜짐

Obj 0x2d (출력)               AddressDest 01 01 01 01   Broadcast 00 00 01 00
                                                                       bit8 켜짐
```

반면 `StartDataBlockIdx` / `EndDataBlockIdx` / `CountDataBlockIdx` 는 **세 요청 모두 `00 01`** 로 같습니다.
즉 **"몇 개짜리 묶음인가" 만 말하고, "몇 번 칸인가" 는 말하지 않습니다.**

> ⚠ **그래서 NCU 는 `AddressDestBroadcast` 비트맵을 반드시 해석해야 합니다.**
> 입력 16칸·출력 8칸을 한 칸씩 받으려면 이 필드 하나로 갈립니다.
> `StartDataBlockIdx` 만 보고 만들면 **언제나 1번 칸만 돌려주는 장비**가 됩니다.
>
> 🟡 다만 **비트 번호 ↔ 포인트 번호 대응은 위 두 표본만으로 단정하지 않겠습니다.**
> 4·5순위 캡처를 뜰 때 **입력 1번부터 16번까지 한 칸씩 훑어서** 비트가 어떻게 도는지
> 표로 만들어 보내 드리겠습니다. 그때 확정해 주십시오.

### 4-3. 응답에서 NCU 가 채워야 할 것

```
offset  1~ 2  FrameLength        = 44 + 234 + (데이터 크기) + 2
offset 42~43  OneDataBlockSize   = 데이터 한 블록 크기   (41 -> 13,  44 -> 21,  45 -> 14)
offset 34~35  StartItemIdx / EndItemIdx  = FF FF     <- 응답에서는 둘 다 FF 로 옵니다
offset 32     DataType           = 00                <- 요청은 01, 응답은 00
offset 44~    장치상태 234 byte  ->  그 뒤에 데이터
```

## 5. 🟢 실측 요청 2번 답 — 리더 주소는 **1부터, 원시 바이트 그대로**입니다

ACU04(실물 SSC-324) 에서 **카드 1회 태그** 하고 그때 올라온 폴링 응답을 그대로 떴습니다.

```
[요청]  이벤트 받기   Cmd 6 / Sub 2 / Obj 01   53 byte
02 00 35 02 80 41 2C 01 01 01 00 00 00 00 00 01 01 01 01 01 00 01 00 01
00 00 00 00 00 06 02 DC 01 01 01 FF 00 01 00 01 00 01 00 00
26 09 14 02 16 04 54                                   <- 데이터 7 byte = BCD 날짜/요일/시각
08 03

[응답]  316 byte  =  44 + 234 + 36 + 1 + 1             <- 이벤트 레코드 1건
offset 42~43  OneDataBlockSize = 00 24 = 36
```

**이벤트 레코드 36바이트 원본**

```
01 02 01 02 01 00 02 01 02 FF 26 09 14 16 04 51 00 00 00 00 FA 76 B1 BD 00×12
```

| off | len | 필드 | 값 | 해석 |
|---:|---:|---|---|---|
| 0 | 1 | Type | `01` | |
| 1 | 1 | Object | `02` | |
| 2 | 1 | Code | `01` | |
| 3 | 1 | Error | `02` | → 이벤트코드 **`01020102`** |
| 4 | 1 | OperationMode | `01` | |
| 5 | 1 | Reserve | `00` | |
| 6 | 1 | **ModuleAddress** | **`02`** | 🔴 **모듈 2 — 1부터입니다** |
| 7 | 1 | **ReaderAddress** | **`01`** | 🔴 **리더 1 — 1부터입니다** |
| 8 | 1 | DoorStatus | `02` | |
| 9 | 1 | FuncCode | `FF` | |
| 10 | 6 | DateTime | `26 09 14 16 04 51` | BCD, YYMMDD HHMMSS |
| 16 | 8 | AccessID | `00 00 00 00 FA 76 B1 BD` | 카드번호 |
| 24 | 4 | RevisionID | `00 00 00 00` | |
| 28 | 8 | Reserve | `00 …` | |

> 🟢 **NCU 가 `(0,0)` → `(모듈 1, 리더 1)` 로 고치신 방향이 맞습니다.**
> 실물이 `모듈 2 / 리더 1` 로 보내고 있고, **원시 바이트 그대로 1부터**입니다. 다른 규칙 없습니다.
> `RRU 번호 하나 = 모듈 2칸`, RRU r 의 첫 모듈 `2r-1` 규칙도 이 값과 어긋나지 않습니다.

## 6. 🟡 덤 — NCU 가 반드시 피해야 할 함정: 이벤트 읽기 인덱스

오늘 저희 현장에서 **SSC-324 한 대(ACU03)가 이벤트를 하나도 올리지 않는** 고장을 잡았습니다.
NCU 가 같은 자리를 새로 만들게 되므로 **설계 전에 보셔야 합니다.**

### 증상

```
카드 태그 -> 폴링 응답 RX 280 byte (데이터 없음)   -> 서버 이벤트 0건
같은 시각 정상 장비   폴링 응답 RX 316 byte        -> 이벤트 1건
요청 프레임은 두 장비가 byte 단위로 완전히 동일
```

### 원인

장비에는 이벤트가 **정상적으로 쌓이고 있었습니다.**

```
이벤트 개수 조회  ->  822 건
카드 4회 태그
이벤트 개수 조회  ->  826 건        <- 정확히 4 증가. 기록은 되고 있다
그런데 폴링 응답에는 계속 0 건
```

⇒ **쌓기는 하는데 "읽기 인덱스" 가 쓰기 위치보다 앞서 나가 버려서, 장비가 "새 이벤트 없음" 이라고 답합니다.**

### 🔴 NCU 설계 시 부탁

| | 내용 |
|---|---|
| ① | **읽기 인덱스와 쓰기 인덱스를 반드시 함께 검사**해 주십시오. 읽기 > 쓰기 상태가 나오면 **자동으로 되돌려야** 합니다 |
| ② | 아래 세 명령을 구현해 주십시오 — 없으면 현장에서 **복구할 방법이 없습니다** |
| ③ | 링버퍼가 한 바퀴 돌 때 인덱스가 어긋나지 않게, 되감김(wrap) 경계를 꼭 시험해 주십시오 |

```
EventCountCheck    이벤트 개수 조회     <- 이 고장을 "장비 문제 / 서버 문제" 로 가르는 유일한 수단
EventIndexChange   읽기 인덱스 이동     <- 복구 수단.  타입 3 = 지정 시각부터,  타입 4 = 시작~끝 구간
EventReset         이벤트 초기화
```

> 🟡 저희는 IDTi 가 함께 배포한 `IntelliScan Device SDK` 로 개수를 읽어 원인을 갈랐습니다.
> **Platinum 과 DM 어디에도 이 세 명령을 누를 화면이 없습니다.** SSC-324 를 대체하실 때
> 이 셋은 **꼭 살려 주시고**, 가능하면 상태(읽기/쓰기 인덱스)도 함께 돌려주시면 훨씬 낫습니다.
