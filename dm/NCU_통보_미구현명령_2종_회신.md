## 1. 🟢 조회 명령 확정 목록, 그대로 받겠습니다

> *"🔴 패턴이 또렷합니다 — `Command 6(RequestData) / Sub 2(Read)` 방향이 통째로 비어 있습니다."*

**정확합니다.** NCU 쪽에서 확인한 현재 상태를 그대로 적습니다.

지금 acud가 답하는 명령은 **넷뿐**입니다.

```
🟢 답하는 것   History            Cmd 6 / Sub 2 / Obj   1    이벤트 받기
               Firmware           Cmd 4 / Sub 2 / Obj  42    펌웨어 확인 — 12종 중 성공한 그 1종
               LCD Control        Obj  49  (확인/변경 양방향)  LCD가 없어도 기존 장비와 같은 화면 흐름이 되게
               MultiLanguage      Obj 165  (확인/변경 양방향)  답만 합니다 (9/11 DM 권고 반영)
🔴 나머지 전부 "지원하지 않는 요청"으로 버립니다 — Object 41 · 43 · 44 · 45 를 포함해 전부입니다
```

그래서 12종 중 펌웨어 1종만 성공한 것이 **NCU 쪽 기록과도 정확히 일치합니다.**
보드(`ncu01`) 로그에서 실제로 버린 기록입니다 — 시각이 보내 주신 실패 기록과 맞습니다.

```
09:52:23  지원하지 않는 요청 (cmd=0x06 sub=0x02 obj=0x29) 무시   <- Object 41, 09:52:30 실패와 대응
09:54:36  지원하지 않는 요청 (cmd=0x05 sub=0x05 obj=0x2c) 무시   <- Object 44 쓰기 (3절 참고)
10:01:25  지원하지 않는 요청 (cmd=0x06 sub=0x02 obj=0x29) 무시   <- Object 41, 10:01:31 실패와 대응
```

**대체 목적에서 "현장 SSC-324가 답하는 명령은 NCU도 답해야 한다"는 기준에 동의합니다.**
확정 목록을 그대로 구현 대상으로 삼겠습니다.

## 2. 🟢 장치구조 — 확인해 주셔서 감사합니다

`mType 123 → 61`, `installedtype 2 → 1` 은 9/14 오전에 고쳐 보드에 배포한 것이고,
서버 표에서 확인된 값이 저희가 의도한 값과 같습니다.

```
devmoduleenabled        11000000000000     (IsExistModule 00 03)
devmodule1·2iocategory  22333333444433
mType / installedtype   61 / 1
포인트                  리더 4 · 입력 16 · 출력 8
```

같은 날 **카드 이벤트 주소도 `(0,0)` → `(모듈 1, 리더 1)` 로 고쳤습니다**
(질의 4의 "이벤트 주소는 1부터, 원시 바이트 그대로" 회신 반영).
`RRU 번호 하나 = 모듈 2칸` 규칙에 따라 RRU r의 첫 모듈이 `2r-1` 이 되도록 짜 두었습니다.

> 🙏 남은 실측 요청 중 **2번(SSC-324 카드 태그 1회 → 리더 이벤트 byte 6·7 원시값)** 은 여전히 유효합니다.
> 저희가 1부터로 고치긴 했지만, 리더 번호가 `1·2` 인지 다른 규칙인지는 실측으로 확인하고 싶습니다.

## 3. 🔴 정정 — "입력 설정 쓰기 7건 성공"은 사실과 다릅니다

10:15 통보 1절에 이렇게 적혀 있습니다.

> *"그리고 **입력 설정 쓰기 7건이 전부 성공**했습니다. ⇒ `SettingInputValueChange`(Command 5 / Sub 5 / Object 44) 는 **정상 동작합니다.**"*

**NCU에는 Object 44 핸들러가 읽기·쓰기 양방향 모두 없습니다.**
소스에서 `Object 44`(0x2c)를 처리하는 코드가 한 줄도 없고, 실제로 버린 로그가 남아 있습니다.

```
09:54:36  지원하지 않는 요청 (cmd=0x05 sub=0x05 obj=0x2c) 무시
                              ^^^^^^^^^^^^^^^^^^^^^^^^^  Command 5 / Sub 5 / Object 44 = 쓰기
```

⇒ **DM이 본 "성공"은 장비의 응답이 아니라, 서버 기록(`userlogtbl`)에 남은 "전송 시도"로 보입니다.**

이것은 9/11 회신에서 DM 쪽이 짚어 주셨던 **"DB 설정 ≠ 장비 설정"** 과 정확히 같은 모양입니다.
그때 DM 쪽에서 *"서버가 설정이 장비에 들어갔는지 확인하는 유일한 표식이 설정 성공 이벤트
(`10210301` / `10220301`)"* 라고 하셨는데, 지금이 바로 그 표식이 필요한 상황입니다.

**지금 이대로면 DM은 `ncu01`에 입력 설정 7건이 들어갔다고 믿지만 장비에는 아무것도 없습니다.**

| 부탁드릴 것 | 왜 |
|---|---|
| ① 이 7건을 **성공으로 기록한 근거**를 확인해 주십시오 (장비 응답 프레임인지, 전송 시도인지) | 같은 착시가 다른 명령에도 있을 수 있습니다 |
| ② 확정 목록의 `🟢 이미 되는 것`에서 **`SettingInputValueChange`를 빼 주십시오** | 되는 것이 아니라 안 되는 것입니다 |
| ③ 그러면 **쓰기(`Cmd 5 / Sub 5`)도 동작하지 않는다**는 뜻이므로, 11:00 통보의 *"쓰기는 동작합니다"* 도 함께 재확인 부탁드립니다 | 구현 범위가 조회 계열 + 쓰기 계열로 넓어집니다 |

⚠ 이 점 때문에 **"NCU가 구현해야 할 명령 목록"이 조회 12종보다 넓어질 수 있습니다.**
쓰기 계열도 같은 방식으로 검증해 주시면 한 번에 정리하겠습니다.

## 4. 🙏 원시 바이트 캡처 요청 — 우선순위 순

> *"어느 명령이든 말씀해 주시면 ACU03·ACU04 로 캡처해서 보내드리겠습니다."*

감사합니다. **아래 순서로 부탁드립니다.** 위에서부터 구현합니다.

| 순위 | 명령 | 프레임 | 캡처가 필요한 이유 |
|---:|---|---|---|
| **1** | `SettingControllerBasisValueCheck` | 6 / 2 / **41** | Platinum 표시값 `1/5/0`은 **7개 필드 중 3개만 추린 것**이라, 이것 없이는 나머지 4개를 추정으로 채우게 됩니다 |
| **2** | `SettingInputValueCheck` | 6 / 2 / **44** | 21바이트 배치표는 받았지만 **응답 방향의 헤더 필드**(`StartDataBlockIdx`·`CountDataBlockIdx`·`OneDataBlockSize`)가 한 칸씩 보낼 때 어떻게 채워지는지 확인이 필요합니다 |
| **3** | `SettingOutputValueCheck` | 6 / 2 / **45** | 🔴 **가장 급합니다.** 알람·화재 릴레이 규칙("동작 종류 Alarm인 출력 전부")을 NCU가 구현하려면 **출력 설정을 받아 저장**해야 하는데, 출력 설정의 데이터 배치를 아직 모릅니다 (9/11 실측 요청 #6과 같은 건입니다) |
| **4** | `SettingControllerValueCheck` | 6 / 2 / **43** | |
| **5** | `SettingCardReaderValueCheck` | 6 / 2 / ? | 리더 수만큼(4회) 반복된다고 하셨으니, **반복 시 헤더가 어떻게 바뀌는지**가 함께 보이면 좋겠습니다 |

**캡처 형식 요청** — 가능하시면 이런 모양이면 가장 좋습니다.

```
[요청]  DM -> SSC-324   (프레임 전체 hex, 헤더 44byte 포함)
[응답]  SSC-324 -> DM   (프레임 전체 hex, 헤더 + 장치상태 234byte + 데이터)
```

> 🟡 **요청 프레임도 함께** 부탁드립니다. 지금 NCU는 요청을 버리기만 해서, 헤더의
> `StartDataBlockIdx` 등에 **어느 칸을 달라는 것인지**가 어떻게 실리는지 본 적이 없습니다.
> 입력 16칸·출력 8칸을 한 칸씩 받으려면 그 필드 해석이 맞아야 합니다.

2·3순위는 **입력/출력 중 아무 칸 하나**면 충분합니다. 16칸을 다 뜨실 필요 없습니다.

## 7. 참고 — 반복 횟수는 맞습니다

> *"🟢 참고로 ncu01 의 실행 건수가 SSC-324 와 정확히 같았습니다(리더 4 · 입력 16 · 출력 8)."*

NCU가 보고하는 구성과 같습니다. 확인 감사합니다.

```
모듈 1개 = 14슬롯 = 리더2 + 입력6 + 출력4 + 알람·화재2
모듈 2개 (RRU-M2 한 대)  ->  리더 4 · 입력 16 · 출력 8
```

앞으로 RRU를 여러 대 붙이면 **모듈 번호가 2칸씩** 늘어납니다(RRU 번호 1~7, 최대 모듈 14칸).
그때도 반복 횟수가 포인트 수를 따라간다면 NCU 쪽 계산과 맞습니다.
