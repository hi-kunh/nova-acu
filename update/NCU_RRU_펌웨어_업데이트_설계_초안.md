> 쓴 쪽: NCU(신규 ACU) 펌웨어 · 작성 2026-09-14

## 0. 한 장 요약

**기존 IDTi 장비에도 DM에도 원격 업데이트 기능이 없습니다.** 그런데 출입통제 장비는 현장에서
10년을 돕니다. 보안 패치든 기능 수정이든 **사람이 현장에 가지 않고 고칠 수 있어야** 합니다.

🟢 **좋은 소식 — 새 프로토콜을 만들 필요가 없습니다.**

```
규약에 이미 범용 파일 전송이 있습니다   (6. IDTi Protocol FileBinaryTransmit.doc)
  Send Start     Cmd 5 / Sub 3 / Obj 0xDD   총 크기(4) + cmd 길이(4) + cmd ASCII(N)
  Send Continue  Cmd 5 / Sub 3 / Obj 0xDE   Index(2) + 원시 데이터 N

그리고 결과를 알릴 이벤트 코드도 이미 있습니다   (event_codes_all.csv)
  18010506  Firmware Update Success
  18010507  Firmware Update Failed
```

⇒ **`cmd ASCII` 한 줄로 "이 파일이 무엇인지"를 말하면 됩니다.**
DM이 보내는 쪽만 만들면 되고, 별도 프로그램으로 가더라도 **같은 프레임**을 쓰면 됩니다.

## 1. 무엇을 갱신하는가 — 셋은 성격이 다릅니다

| 대상 | 무엇 | 크기(예상) | 실패하면 |
|------|------|---:|------|
| **ACU 응용** (`acud`, webui) | 실행 파일 묶음 | 수 MB | 서비스만 되돌리면 된다 |
| **ACU 시스템** (커널·루트파일시스템) | OS 이미지 | 수백 MB | **A/B 파티션으로 통째로 되돌린다** |
| **RRU 펌웨어** (STM32C562) | `.bin` | 수십~수백 KB | **RRU가 벽돌이 되면 함체를 열어야 한다** ← 가장 위험 |

> ⚠ **이 셋을 한 가지 방법으로 묶지 마십시오.** 위험도와 되돌리는 방법이 다릅니다.
> 아래 절차도 셋을 따로 적었습니다.

## 2. 전달 경로 — 셋 중 무엇으로 갈 것인가

| | 방법 | 장점 | 단점 |
|---|------|------|------|
| **(가)** | **DM이 규약 파일 전송(`0xDD`/`0xDE`)으로 내려보낸다** | 이미 깔린 연결·화면을 그대로 쓴다. 현장에 새 프로그램을 안 넣어도 된다 | **DM 쪽 개발이 필요하다** |
| (나) | **별도 업데이트 프로그램**이 ACU에 직접 붙는다 | DM을 안 건드린다. 우리가 일정을 쥔다 | 현장에 프로그램을 하나 더 깐다. 망·방화벽·권한을 또 정해야 한다 |
| (다) | USB 메모리·SD로 사람이 꽂는다 | 가장 단순. 망이 끊겨도 된다 | **사람이 현장에 가야 한다** — 만들려는 이유가 사라진다 |

### 🟢 권고: **(가)를 기본, (나)를 같은 프레임으로**

```
DM ──(규약 0xDD/0xDE)──> ACU ──(ACU↔RRU USB 프로토콜)──> RRU
              ↑
       별도 프로그램도 **똑같은 프레임**으로 붙는다 (ACU 쪽은 구분하지 않는다)
```

- ACU는 **보낸 쪽이 DM인지 별도 프로그램인지 구분하지 않습니다.** 같은 TCP 포트, 같은 규약입니다
- 그래서 **DM 개발이 늦어도 별도 프로그램으로 먼저 쓸 수 있고**, 나중에 DM이 붙어도 ACU는 그대로입니다
- (다)는 **최후 수단**으로 남깁니다 — 망이 죽었거나 업데이트가 실패해 되돌릴 때

## 3. `cmd ASCII` — "이 파일이 무엇인가"

규약이 `cmd ASCII`를 **자유 문자열**로 두었습니다. 여기에 규칙을 정합니다.

```
NCU-FW <대상> <판> <크기> <해시>

예)
NCU-FW acu-app     1.2.0   5242880  sha256:3f9a...  ACU 응용 묶음
NCU-FW acu-system  2026.09 314572800 sha256:8c11... ACU OS 이미지 (A/B)
NCU-FW rru-m2      1.0.5   131072   sha256:a7e0...  RRU-M2 펌웨어
```

| 자리 | 내용 |
|------|------|
| `NCU-FW` | 이 파일이 펌웨어 갱신임을 나타내는 표식. **다른 용도의 파일 전송과 섞이지 않게** |
| 대상 | `acu-app` / `acu-system` / `rru-m2` / `rru-m4` … **모델명과 같은 이름** |
| 판 | 사람이 읽는 판. 내림 금지 판단에 쓴다 |
| 크기 | byte. Start의 `총 크기(4)`와 **같아야 한다** (어긋나면 거절) |
| 해시 | **`sha256:` 접두 + 16진수.** 다 받은 뒤 반드시 확인한다 |

> 🟡 `cmd ASCII`가 규약에서 길이 제한이 없어 보이지만, 실제로는 첫 프레임에 들어가야 합니다.
> **256byte 안쪽**으로 제한하기를 제안합니다.

## 4. ACU 갱신 절차

### 4-1. 응용(`acud`, webui)

```
1. Start(0xDD)    cmd 확인 -> 대상·판·크기·해시 기록, 임시 파일 열기
2. Continue(0xDE) 조각을 임시 파일에 이어 쓴다   (사용자 바이너리와 같은 조각 규칙)
3. 다 받으면      크기·해시 확인.  틀리면 버리고 18010507(Failed)
4. 설치           새 파일을 **옆에 두고** 원자적으로 바꿔 끼운다 (rename)
5. 재시작         systemd가 acud를 다시 띄운다
6. 확인           30초 안에 자기 확인(스스로 살아 있는지)에 실패하면 **직전 것으로 되돌린다**
7. 보고           18010506(Success) 또는 18010507(Failed)
```

- **받는 동안 출입 판정은 계속됩니다.** 새 파일은 옆에 쌓일 뿐입니다
- 되돌릴 것 하나는 **항상 남겨 둡니다** (직전 판)

### 4-2. 시스템(OS 이미지) — A/B 파티션

이미 정해 둔 방향입니다 (HARDWARE.md "최종 OS" 절 — 자체 빌드 / 메인라인 커널 / **A-B 파티션**).

```
지금 A로 돌고 있다  ->  받은 이미지를 B에 쓴다  ->  다음 부팅을 B로 표시  ->  재부팅
    B가 정상 부팅하고 자기 확인을 통과하면  ->  B를 확정
    실패하면 부트로더가 **자동으로 A로 되돌린다**  (시도 횟수 제한)
```

- **되돌리기가 사람 손을 타지 않아야 합니다.** 부트로더가 판단합니다
- 이미지가 수백 MB라 **받는 데 오래 걸립니다** — 진행률 보고가 필요합니다(6절)

### 4-3. ⚠ 언제 하면 안 되는가

| 막아야 할 때 | 왜 |
|---|---|
| **강제 개방(화재) 중** | 화재 상황에 문 제어가 끊기면 안 된다 |
| 사용자 명단을 받는 중 | 반쪽 명단 + 재시작이 겹친다 |
| 이벤트가 많이 밀려 있을 때 | 재시작으로 전송이 더 밀린다 (보관은 되지만 DM 화면이 늦어진다) |

⇒ **ACU가 "지금은 안 된다"고 거절할 수 있어야 합니다.** Start에 Fail로 답하고 사유를 이벤트로 남깁니다.

## 5. RRU 갱신 절차 — 가장 위험한 곳

**RRU가 벽돌이 되면 함체를 열어야 합니다.** 그래서 여기만 규칙을 더 답답하게 잡습니다.

```
DM/도구 ──0xDD/0xDE──> ACU (파일을 다 받아 해시 확인) ──ACU↔RRU USB──> RRU
```

- **ACU가 먼저 파일 전체를 받고 해시를 확인한 뒤**에 RRU로 보냅니다.
  조각을 그대로 중계하면 중간에 끊겼을 때 RRU가 반쪽 펌웨어를 쓰게 됩니다
- RRU는 **받는 동안에도 정상 동작**해야 합니다 (카드·입력을 계속 올린다).
  쓰기는 다 받은 뒤 한 번에 합니다
- RRU에 **되돌릴 자리(두 벌)** 가 있으면 가장 좋습니다. STM32C562 플래시가 부족하면
  **부트로더만이라도 절대 지워지지 않게** 하고, 실패 시 부트로더가 다시 받을 수 있어야 합니다

### RRU 쪽 프로토콜 — 이미 자리를 비워 뒀습니다

`rru/ACU_RRU_USB_프로토콜_설계_초안.md` 10절 8번에서 **TYPE `0x50~0x5F`를 펌웨어 갱신용으로
예약하자**고 물어 두었습니다. 제안하는 모양:

| TYPE | 이름 | 방향 | 내용 |
|---:|------|------|------|
| `0x50` | `FW_BEGIN` | ACU → RRU | 대상·판·총 크기·해시(32) — RRU가 받을지 답한다 |
| `0x51` | `FW_DATA` | ACU → RRU | 조각 번호(2) + 데이터 |
| `0x52` | `FW_END` | ACU → RRU | 다 보냈다 — RRU가 해시를 확인하고 쓴다 |
| `0x53` | `FW_STATUS` | RRU → ACU | 진행률·결과 |

> ⚠ **`FW_BEGIN`에서 RRU가 거절할 수 있어야 합니다** — 판이 같거나 내림이거나,
> 플래시가 모자라거나, 지금 쓰면 안 되는 상태일 때.

## 6. 상태·진행률 보고 — 새 이벤트 코드를 만들지 않습니다

**우리는 새 이벤트 코드를 만들 수 없습니다** (기존 IDTi 장비 대체가 원칙). 다행히 있습니다.

| 코드 | 이름 | 언제 |
|------|------|------|
| `18010506` | Firmware Update Success | 갱신 성공(대상별로 1건) |
| `18010507` | Firmware Update Failed | 실패(사유는 로그에) |

- 이벤트 주소는 **대상이 무엇인지**로 나눕니다: ACU는 `(첫 모듈, 0)`, RRU r은 `(2r-1, 0)`
- **진행률은 이벤트로 올리지 않습니다.** 몇 백 건이 DM 이벤트 목록을 덮습니다.
  대신 **파일 전송의 조각 응답(Success/Fail)이 곧 진행률**입니다 — 보낸 쪽이 셀 수 있습니다
- 🟡 더 자세한 상태가 필요하면 **별도 조회 오브젝트**를 하나 정해야 합니다 (9절 결정 사항)

## 7. 안전 장치

| | 내용 |
|---|------|
| **해시 확인** | `sha256`. 다 받은 뒤 **반드시** 확인하고, 틀리면 설치하지 않는다 |
| **서명** | 🟡 결정 필요 — 해시만으로는 "깨지지 않았다"만 알고 "우리가 만든 것"인지는 모른다 (9절) |
| **판 내림 금지** | 기본은 거절. 되돌릴 때만 **명시적인 강제 표시**로 허용 |
| **대상 확인** | `cmd`의 대상과 실제 장비가 다르면 거절 (`rru-m4` 파일을 `RRU-M2`에 쓰지 않는다) |
| **전원** | 쓰는 동안 전원이 끊겨도 **되돌릴 수 있어야** 한다 — A/B와 RRU 부트로더가 그 역할 |
| **중복 실행 금지** | 한 번에 하나. 받는 중에 또 Start가 오면 앞의 것을 버리고 시작할지 거절할지 **정해야 한다**(9절) |

## 8. 최후 수단 — 망이 죽었을 때

원격 갱신이 실패해 **장비에 접근할 방법이 없어지는 것**이 가장 나쁩니다.

- ACU: A/B 파티션이 자동으로 되돌립니다. 그래도 안 되면 **USB 메모리로 복구 이미지**
- RRU: ACU가 다시 보냅니다. ACU까지 죽었으면 **함체를 열고 SWD**
- ⇒ **함체를 열지 않고 복구할 수 있는 길을 하나는 남겨 둡니다**

## 10. 하지 않기로 한 것 (지금은)

- **자동 갱신** — 장비가 스스로 새 판을 찾아 받는 것. 출입통제에서는 위험이 이득보다 큽니다
- **여러 대 동시 갱신** — 먼저 한 대씩 확실히 되게 하고, 묶음은 그다음입니다
- **차등 갱신(delta)** — 파일이 작아 필요가 없습니다. 통째로 보냅니다
